## 4. Per-topic research

### 4.1 Three versions newer than ours: not a free upgrade opportunity

The release page identifies **r186 as latest**; the migration guide already has **186→187**, which is upcoming development, not evidence of an available stable upgrade [V1,V2]. Distinguish renderer names carefully: many release bullets headed `Renderer`, `Backend`, or `WebGLBackend` affect the new renderer architecture rather than this app's classic WebGLRenderer. WebGPU/renderer migration is explicitly out of scope.

Perf/correctness changes sometimes suggested online are **already in ours**: r186 includes compileAsync disposed-material safety (#34378), BatchedMesh color checks (#34056), setGeometryIdAt visibility invalidation (#34096), image bitmap loader fixes, optimized readRenderTargetPixels capability checks (#34183), PBR multiscattering/DFG/shader changes [V1]. compileAsync uses KHR_parallel_shader_compile today and Engine already guards extension availability. It warms scene materials, not arbitrary composer fullscreen scenes, first draw uploads or every shadow/effect variant. Do not conflate deferred PassNode/WebGPU compileAsync with this code.

BatchedMesh is already used for the fleet. Its effective multi-draw acceleration depends on WEBGL_multi_draw availability, not just a new JS class. WebGL2 is available across current Chrome/Firefox/Safari, but KHR_parallel_shader_compile, WEBGL_multi_draw, EXT_clip_control and GPU timer extensions remain implementation/driver dependent; query once and retain existing supported paths, never browser-name assume availability. Reversed depth is already an r186 option, requires EXT_clip_control, and improves depth precision vs logarithmic depth, not an intrinsic throughput guarantee [V3]. This app has near/far5/9000 and does not enable logarithmic depth; replacing a gl_FragDepth log-depth path therefore cannot be counted as a saving here.

Upcoming r187 replaces CubeUV PMREM storage with cube targets and changes setViewport/setScissor render-target DPR behavior, adds WeakRef/FinalizationRegistry use, and removes CubeUVReflectionMapping [V2]. The PMREM PR reports **M1, 1080p30-sphere scene, synchronized warm median63 alternating pairs across3 runs, WebGL3.14→2.36ms (~25%)**, with generation excluded;1K generation got slower9.85→10.38ms,2K faster25.12→20.03ms [V4]. It also changes energy/roughness/filtering; discussion identifies aliasing differences. **Our runtime source search found no PMREM/CubeCamera usage**, consistent with orchestrator confirmation. Thus this benchmark is not grounds for a25% PharosVille claim.

**Upgrade risk note:** high visual/regression risk relative to presently unproven speed gain. `world/materials.ts:528-601,615-637,655-718`, `fleet/fleet-material.ts:392-438`, civic/life/identity/readings hooks all replace shader chunk strings. A compile success does not prove replacements still match; upgrade must check the actual transformed shaders, shadow variants, custom depth material, AgX/LUT, fog/beam depth, transparent sails, viewport/DPR behavior and postprocessing/n8ao peer compatibility. Keep @types/three synchronized. Reversed-depth migration must migrate every custom depth reconstruction/comparison, not merely constructor option. Recommended verdict: **retain r186 in this optimization cutover**, evaluate later stable release only with target-device evidence and visual parity.

### 4.2 KTX2/BasisU, UASTC vs ETC1S, AVIF/WebP

KTX2 is a texture container, BasisU a portable intermediate codec; neither is a native `<img>` replacement. KTX2Loader parses/transcodes in workers into a GPU-supported format [T1]. ETC1S targets low/medium quality and small transmitted files (~0.3–3bpp according to Basis source); UASTC LDR4×4 is8bpp before RDO/Zstd, higher quality, with especially cheap ASTC/BC7 transcoding [T2]. Both can bundle mipmaps and avoid uploading full RGBA8 images. GPU compression format support is hardware-dependent even in the same browser; use detectSupport(renderer). Current Chrome, Firefox and Safari support the WASM/WebGL2 ingredients, but exact output differs (BCn/ETC2/ASTC and alpha variants).

The downloaded raw decoder size is **527KB WASM+58KB wrapper**, gzip WASM alone245KB; that extra network, WASM instantiation and worker setup can lose against existing1.48MB AVIF if KTX2 is not substantially smaller or if only a small texture is converted. No trustworthy universal transcode-milliseconds claim was found for this exact decoder/atlas/device combination; measure worker startup, transcode and first GPU upload separately. RGBA8→BC7/ETC2 RGBA is4× less resident texel data; BC1/ETC1 RGB is8× if alpha is not needed. These are format arithmetic, not measured FPS gains. Khronos explicitly explains resident-memory/bandwidth advantages but gives no PharosVille benchmark [T3].

**Important CSP constraint:** wasm-unsafe-eval permits WASM compilation but not blob workers. Installed KTX2Loader:329-334 and meshopt useWorkers:113-117 create blob workers. With no worker-src/child-src, CSP falls back to script-src [T4], which has self but no blob:. A narrow worker-src policy including self/blob: (or a real same-origin custom worker implementation) is necessary; do not loosen script-src to unsafe-eval. Workers/worker limits need checking on all three browser engines.

**Do not claim AVIF/WebP always decode on the main thread.** Native codecs use browser-controlled asynchronous/background paths; createImageBitmap and img.decode provide explicit async completion. This app's emblem/SDF paths already use createImageBitmap. Main-thread work still includes canvas packing/readback, JS texture creation and upload submission, and GPU work may synchronize. Preserve colorspace, alpha premultiplication, vertical orientation and atlas gutters. Sea-SDF is exact CPU-readable data for topology/placement: a lossy Basis replacement can change the world's meaning; exclude it unless keeping an exact separate CPU representation and proving unchanged semantics. The newest Basis2.5 modes on upstream master are **not** automatically compatible with Three's pinned transcoder; focus on conventional ETC1S/UASTC LDR4×4, not speculative codec upgrades.

### 4.3 Meshopt SIMD, filters and Draco

The installed vendored decoder already uses WASM.validate to select SIMD (`meshopt_decoder.module.js:11-26`). Current browser engines support WASM SIMD (Chrome91+, Firefox89+, contemporary Safari); no cross-origin isolation/SharedArrayBuffer is required for single-worker SIMD. wasm-unsafe-eval is already present. Meshoptimizer documents **1–3GB/s desktop decoding** [G1]; this is decoded bytes, not compressed network throughput, and excludes JS GLTF scene construction/uploads.

EXT_meshopt_compression modes are ATTRIBUTES/TRIANGLES/INDICES and filters **NONE/OCTAHEDRAL/QUATERNION/EXPONENTIAL** [G2]. Octahedral is appropriate for normals/tangents, quaternion for rotation, exponential for float data. **COLOR is a newer KHR filter, not an EXT filter**. Filters themselves do not shrink the decoded buffer size; they improve entropy, often following precision reduction. Quantization creates the GPU storage saving. Attribute codec is lossless over encoded bytes, but the preceding quantization/scene rewrite may not be. gltfpack can merge/reorder/prune node trees, discard unknown custom attributes and resample animations; preserve PharosVille's names, extras, pattern data, morph/kit contracts explicitly [G4].

Upstream1.2 reports **5–10% JS decoder speedup**, not the20–45% SSSE3 native C++ speedup in the same release [G3]. Runtime decoder update may be easy but small.1.1.1 also fixes a rare high-level v1 SIMD decoding case; verify whether the vendored1.1 file includes that fix before producing aggressive KHR v1 content. Browser support is a loader+decoder capability question; r186 GLTFLoader advertises both EXT and KHR.

Draco is a separate Google geometry codec/glTF extension [G5], not a different meshopt setting. It can offer attractive geometry ratios, but there is no credible universal “Draco always smaller” or fixed decode ratio. It requires a second decoder download/worker initialization and another loader path; topology/order/custom attributes need equal-care checking. For this already-meshopt-enabled pipeline, measure both only if Draco materially beats **meshopt+HTTP gzip** at identical precision and source semantics; do not replace a working fast decoder on compressed-size folklore. No decoder swap improves steady-state rendering by itself. Meshopt async workers can keep decode off main but introduce transfer/startup cost and current blob-CSP issue; a few MB at GB/s often does not justify multiple workers.

### 4.4 pmndrs postprocessing

EffectPass merges compatible pointwise operations into a compound shader [P1]. **Already done** for the main art pass; counting five effect objects as five full-screen passes is wrong. Also, merging effect composites does not eliminate internal bloom blur, luminance, tilt-shift or SMAA work. Two convolutions reading the same original input are not equivalent to sequential image processing; moving SMAA into the same pass may change output. Preserve intentional ordering, colorspace and HDR semantics.

The8-level mipmap bloom has8 downsample+7 upsample draws.6levels yields6+5, saving4 small draws but only about **0.057%** of the blur-chain output pixels by geometric-series calculation (excluding luminance), because removed levels are tiny. This can reduce submission/target switches and change halo radius, but **not25% bloom fill cost**. Most work lies in luminance and the top mip levels [P3]. Installed6.39.5 BloomEffect.setSize forwards full input dimensions to luminancePass and mipmapBlurPass: changing deprecated BloomEffect.resolutionScale does **not** scale this active mipmap path. Real lower-resolution bloom needs actual target sizing; render-pipeline slice is separately investigating this.

Keep HalfFloatType for HDR bloom+AgX. RGBA16F is8bytes/texel vs RGBA8's4, but switching to8-bit can clip bright values and band dark sea/night gradients; removing half-float is not scenery-neutral. Conversely RGBA32F→RGBA16F halves storage, but ours is already16F. MSAA must be on composer targets, not canvas antialias; that false flag is already correct [P2]. SMAA uses edge/weight/composite stages and lookups; FXAA is typically one pass but can blur emblem/rigging details. MSAA has sample/resolve overhead and depth-effect caveats, and does not fix all shader aliasing. No universal credible GPU-ms gain exists across these choices; target-GPU timestamps and moving shots are mandatory.

### 4.5 WebGL2 best practices

MDN's primary practical guidance [W1] matches the warm first-render issue:

- Avoid sync readPixels/getBufferSubData/getError/getParameter and premature shader-status queries; use fences/PBO async readback or precompute immutable CPU data. **Do not remove error checks as a substitute for fixing a fault**. Three exposes readRenderTargetPixelsAsync already [V3].
- Batch shader compile/link and poll KHR completion rather than serially requesting blocking status; Engine partly already does this. Prewarm actual effect/depth variants and initTexture/initRenderTarget where a measured dependency permits overlap; moving all the same blocking work earlier without overlap does not reduce total boot.
- texStorage+texSubImage establishes immutable sized storage and avoids driver guessing/full-mip overallocations; audit Three's existing implementation before duplicating raw GL.
- Keep stable FBO/VAO attachments, reuse targets, upload textures before drawing rather than in the middle of a pipeline; mipmaps cost roughly33% memory but reduce distant texture bandwidth/aliasing.
- invalidateFramebuffer can avoid stores on tile GPUs when an attachment is truly dead. Never invalidate scene depth before fog/shafts/picking use it. Tiled mobile/iGPU architecture benefits differ from the supplied RTX.
- Avoid unnecessary RGB emulation, precision changes, antialias/preserveDrawingBuffer requests. Engine already stencil false, antialias false; no blanket constructor tuning should be credited again.
- Newer WEBGL_provoking_vertex can reduce emulation where flat interpolation is used, but requires vertex convention correctness and supported-driver proof; no sourced scene gain, so not a priority.

Core WebGL2 storage/readback/invalidation methods work across current Chrome/Firefox/Safari. Float renderability, timer, multidraw and compressed-format extensions still require feature/hardware detection. Timer queries must be polled only when available and disjoint results discarded [Q1]; governor already does this. No new glFinish/flush call belongs in each rAF frame: MDN says rAF's frame boundary already provides submission pressure.

### 4.6 Cloudflare Pages, hints, compression and API placement

**Pages static assets already use Tiered Cache automatically** [C1]. Browser cache freshness is separate from edge residency; no max-age for /harbour means revalidation, not “CDN never caches GLB.” Fingerprint public assets first, then long-cache in browser. Cloudflare explicitly warns that broad custom Cache Rules can serve stale deploys and bypass redirects/Functions. Never cache-everything /api or HTML to fix a static byte issue.

Pages Early Hints is **always enabled**, including custom domains [C2]. It emits cached Link preloads/preconnects. Auto-Link extraction accepts only href/as/rel; **any extra attribute, including media, crossorigin or fetchpriority, suppresses auto generation**. That protects our gated asset hints. An unconditional manual Link for island/app would fetch world bytes on rejected viewports, violating the hard contract. Keep the gate and matching fetch credentials; at most evaluate universally-needed shell hints. Browsers process103 under H2/H3, but exact preload hint handling varies; Chrome103+ supports it [C7]. Do not infer live103 behavior from local Vite or a final-response header alone.

Cloudflare default compression types include JS/CSS/JSON/WASM/SVG/fonts but **not model/gltf-binary**, AVIF/WebP or KTX2 [C3]. Our preencoded gzip GLBs solve a real default gap. Compression Rules can select algorithms by media type/extension; all plans have some rules, custom domain must be proxied, no-transform prevents changes, and a rule with no supported algorithm sends uncompressed [C4]. Retain gzip/br fallbacks. Current docs distinguish generic zone defaults (Free zstd; Pro/Business br; Enterprise gzip) from Pages serving behavior; **measure this site's actual negotiated encoding**, never assume all Cloudflare traffic uses Brotli. Ordinary br works on all three engines; zstd is Chrome123+, Firefox126+, **Safari26.3+ with OS constraint** [C8]. Existing encoded Pages responses may carry no-transform; a zone rule is not proof the platform will transcode a preencoded asset.

Pages Functions can use caches.default on pages.dev and custom domains [C5]. It is local to the invoking POP, **cache.put is not Tiered Cache**, match does not fetch upstream on miss, and Cache API ignores stale-while-revalidate/stale-if-error semantics. Authenticated upstream calls need careful public-response selection; never include API keys in public cache keys/URLs or cache errors. Upstream fetch cache integration and existing headers may already solve it; inspect before layering caching.

Smart Placement applies to Functions, not normally static files; it helps chatty/compute-near-data code, not automatically a thin one-request proxy [C6]. Global middleware or env.ASSETS.fetch can accidentally pull static delivery to backend location. No universal milliseconds result is supplied by these docs; prefer geographic p50/p95 experiments if API owner sees backend latency, with operator-owned configuration.

### 4.7 Chrome loading features and repeat visits

fetchpriority: Chrome102+, Firefox132+, Safari17.2+ [L1]. modulepreload: Chrome66+, Firefox115+, Safari17+ [L2]. The latter can fetch/parse/compile modules before import evaluation and may recursively fetch dependencies; explicit flat dependency list is good cross-browser practice, and Vite already generates that here. Resource priority is a relative hint, not a guaranteed HTTP schedule. Literature: Google Flights experiment improvedLCP2.6→1.9s using Fetch Priority [L1]. **Not** a700ms predicted improvement here; island is already low priority and poster path is already optimized.

Compression Dictionary Transport uses previous JS or a learned shared dictionary plus dcb/dcz to transmit differences [L5]. Google Search measured23% average HTML-byte reduction vs Brotli across Chrome users,1.7% overall LCP gain/up to9% high-latency, with one107→60KB example. This is rigorous motivation, not a claim for a static SPA. Chrome130+ ships; current MDN BCD lists Firefox preview/145behind preference, Safari unsupported [L8]. Same-release immutable cached JS beats any delta download; only cross-release repeat visitors benefit, dictionary bytes amortize over later use, and Vite hash changes/chunk churn determine similarity. Ordinary Cloudflare zstd != dictionary transport. No read primary source established transparent native Pages dcb/dcz deployment, so a custom protocol-aware edge path is prerequisite, not a free header switch.

Explicit compile hints: Chrome136+ file-level magic comment; current explainer says no non-Chromium implementation and function-level hint still experimental [L3,L9]. V8 reports17of20 popular pages improve, average630ms foreground parse/compile reduction; Workspace prototype5–7% userland load metric. These much larger apps are not our baseline. Our classes and renderer bundle include code not used at boot, so hinting the entire vendor/app chunk may regress. Use measured coverage and preserve top-of-file comments in output.

V8 code caches reward unchanged script URL/content and stable libraries [L6]. Stable vendor splitting is already present; don't add cache-busting timestamps or synthetic version query strings to unchanged chunks. Engine heuristics are implementation details, not a promise. Especially **do not claim service-worker precaching forces full ESM bytecode caching**: the V8 article explicitly notes its historic full precache assumes classic scripts and ES modules discard/replace it.

bfcache is in Chrome/Firefox/Safari and preserves the page heap rather than just bytes [L4]. It can avoid world rebuild on actual back/forward document return, not camera/view changes. Current source search did not find unload. Preserve eligibility; test pageshow.persisted, context-loss recovery, clock and stale live-data refresh. Successful eligibility is not guaranteed on memory-heavy WebGL pages.

Speculation Rules targets future documents, not glTF/images/subresource fetches [L7]. Current web-features compatibility snapshot lists **Chrome109+; Firefox and Safari unsupported**. Inline rules also need CSP permission absent here; header-based rules are possible. **Irrelevant to optimizing this one running world**, and prerendering a second world burns memory/GPU/data. Do not introduce it.

### 4.8 OffscreenCanvas/worker rendering

Feasible in principle with Three WebGLRenderer: its canvas option accepts OffscreenCanvas [V3,O1]. MDN BCD reports worker WebGL2 context Chrome69+, Firefox105+, **Safari17+**; generic OffscreenCanvas Safari16.4 is not sufficient for WebGL [O2]. Some old Three manual search snippets still say Chrome-only; direct manual URLs returned404, so that stale compatibility prose was not used.

DOM overlay is not intrinsically incompatible: keep React/input on main and transfer a canvas to a rendering worker. The conflict is current ownership, not browser impossibility. Engine directly touches HTMLElement append/size, document visibility, addEventListener/devicePixelRatio/location/window debug stats; CameraInput needs main-thread event forwarding; textureLoader uses DOM image loading; React's data/selection/overlay access needs snapshots/proxies rather than live scene references. Scene objects cannot simply be structured-cloned. Need bounded messages, transferable typed arrays for bulky state, worker-side ImageBitmap/image decode, lifecycle/context loss, disposal and back-return handling. DOM screen-space labels must track camera without a message backlog. Main thread still handles UI/input/presentation; GPU remains the same. No evidence justifies reopening the prior worker rejection for a wholesale renderer move before eliminating measured boot/readback/scene work. Use same-origin module workers to stay within CSP, not blob workers by accident.

### 4.9 Adaptive resolution / variable-rate rendering

Existing governor already implements the modern essentials: GPU-sensitive decisions, no scale-down on CPU-bound frames, cooldown, hysteresis and extension-free fallback. Do not add a parallel adaptive controller. Scaling dimensions by0.85 cuts raster pixels27.75%, but never simulation, geometry vertex work, shadow pixels unless explicitly resized, JS parsing or shader compile. A frame with50% pixel-bound cost improves at most~13.9% before overhead, not27.75% globally. Changing render target sizes every frame is counterproductive; preallocation/low-frequency changes avoid churn.

WebGL2 has **no standard broadly-available hardware variable-rate shading API**. Practical “variable rate” means effect-specific lower-resolution targets (bloom/fog/shafts), temporal refresh of slow-changing passes, or idle frame pacing. Temporal reuse requires correct invalidation on camera/weather/light/scene change; animated water and fleets prevent generic on-demand rendering of the whole world. A30Hz cap can halve submitted frames/work over time but visibly changes motion; not no/marginal scenery impact by default. DOM can stay full-resolution independently. Use existing quality ladder for pixel-bound devices, prioritize independent low-frequency effects before lowering the whole1× scene.

### 4.10 Service worker strategies for a large static 3D app

Service workers/Cache Storage work in current Chrome/Firefox/Safari on HTTPS [S1]. Good optional pattern: versioned static cache-first, populate only requested world resources after admitted first frame, bounded size, atomic manifest+revision, remove obsolete caches during safe activation, handle failed writes/eviction, and network-first HTML/update coordination. Navigation preload can hide worker startup for network navigations [S2], but cannot improve a first visit before a worker exists.

Do **not** precache all media during SW install: small/welcome viewports must never fetch world, install competes with first-frame downloads, speculative unused assets waste storage, and addAll failure can reject an entire install. Do not use cache-first or unmarked stale-while-revalidate for /api: a living financial world must preserve freshness/unavailable semantics. Cache Storage does not honor HTTP freshness automatically. A SW is not a trusted source of permanent persistence; storage can be evicted and denied. Correct immutable HTTP caching already avoids most static repeat transfers without another update lifecycle. Verdict: optional product-level repeat/offline feature, **not first-line speed fix**. No source supports a guaranteed cold-load saving; likely zero incremental speed once EXT-01 is implemented.

## 5. Ruled out / not worth it

- Generic Three upgrade to obtain compileAsync, BatchedMesh, half-float, SIMD or texture prewarming: APIs/optimizations already present; r186 latest stable. No renderer switch/WebGPU proposal.
- Blindly applying gltfpack default prune/merge/quantize to all kits: could discard attributes or node/extras contracts and alter meaning. Codec/storage optimization itself remains valid after preserving contracts.
- Replacing sea-SDF/exact masks with lossy ETC1S: potentially changes topology/navigation, not mere scenery.
- “AVIF decode is on main, so KTX always loads faster”: false premise and ignores245KB gzip transcoder plus startup.
- “Drop8bloom levels to6 for25% lower fill”:4tiny draws saved, ~0.057% blur pixel reduction; radius/art also changes.
- “Set BloomEffect.resolutionScale=.5” as a mipmap optimization: deprecated setting does not size active mipmap/luminance path in6.39.5.
- Merge all convolution/AA/scrub passes indiscriminately: violates input/stage semantics, can let NaNs propagate through bloom. Fix source or prove ordering.
- Replace HDR composer with8-bit or switch all shaders to mediump: obvious banding/overflow/precision risk, no parity evidence.
- Enable Tiered Cache or cache-everything for Pages: static tiering already automatic; cache rules can break deploy freshness/Functions.
- Ungated world103 Link headers: breaks mandatory desktop/viewport gate. Missing automatic103 for media links is not automatically a defect.
- Dictionary Transport/service worker as initial-load magic, or copying Google Search/V8 headline percentage into our plan: different workloads and often zero cold benefit.
- Speculation prerender of camera/hour permutations; hardware VRS/foveation; global30Hz; wholesale worker renderer rewrite before profiling: unjustified or visual/architecture risk.
- Synchronous GPU query spam or forced gl.flush inside each rAF to “finish uploads”: causes/maintains serialization rather than reducing work.

## 6. Open questions / operator decisions

1. Which supported Safari/OS floor must be retained? Offscreen WebGL2 requiresSafari17; zstd needsSafari26.3with OS support, but br fallback solves compression compatibility without changing the app floor.
2. Are custom-domain zone Compression Rules/settings accessible, and what encoding actually reaches users for JS/JSON/model MIME types? Requires live edge/header evidence from delivery slice, not generic docs.
3. Is a narrowly scoped worker-src self+blob policy acceptable for stock KTX2/meshopt workers? wasm-unsafe-eval alone is insufficient. A same-origin worker implementation avoids blob permission but is more engineering.
4. KTX candidates need art approval across desktopBC7, mobileETC2/ASTC, alpha/mips and closest readable emblems; no asset variant tested in this slice. Keep data masks exact.
5. If proposing API edge caching, does existing proxy/upstream already cache and what exact freshness contract must remain? An extra stale window is not automatically acceptable.
6. Does live back-return already hit bfcache, and do data/context/clock resume correctly? If yes, there is no change opportunity.
7. Would offline SW behavior or belowDPR1 rendering be acceptable product choices? Neither should enter the no/marginal implementation cutover without explicit acceptance.
8. No blocker to this research report. Actual gains require the measurement/asset/rendering slices; source-derived estimates intentionally do not claim rendered parity or observed ms savings.
