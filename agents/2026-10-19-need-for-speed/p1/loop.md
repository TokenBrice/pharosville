## 2. Current loop / idle behaviour

### Scheduling and time

- `Engine.start()` owns a single manual `requestAnimationFrame` chain; `running` prevents duplicate starts; the next callback is scheduled **before** `frame()` (`engine.ts:168–180`). No `renderer.setAnimationLoop()` is used. Swapping API alone does not eliminate any updates or draws.
- Every callback runs every ready system and the entire composer, regardless of camera movement, reduced motion, unchanged data, or input inactivity (`engine.ts:182–208`). Normal frame object and stats object are reused; there is no new `FrameState` per frame.
- Delta is clamped to `[0,0.1]` seconds; elapsed advances by this clamped delta, not real wall time. This prevents huge simulation steps after stalls but slows decorative/simulation time during repeated stalls. `frame.nowMs=Date.now()` remains wall time. Visibility resume resets `clock.last`, so hidden duration does not become a huge catch-up step (`engine.ts:171,186–190`). A future FPS cap must accumulate the delta between **executed** world frames, not update `last` on every skipped rAF.
- `document.hidden` stops/cancels the engine rAF; visible restarts it (`engine.ts:68,100,180`). This already handles tab backgrounding/minimization when the browser changes Page Visibility. Merely covering a window, scrolling the canvas out of view in a different shell, or OS occlusion without a visibility event has no explicit application-level guard. Browser compositor throttling is not an application guarantee. Hidden initial boot is not guarded by `start()` itself, although browser rAF is normally suspended.
- **The historical “frame duty halves after three minutes without input” is not present at HEAD.** It appears in the old Garden changelog (`src/content/pharosville-changelog.ts:464`), not in the current engine/input/UI loop. There is no inactivity timer or render skip. Do not report this as already shipped in the Harbour or silently rely on it.
- Reduced motion is a service that eases decorative `MotionClock` toward zero (`ui/services.ts:53–94`), not an engine stop/on-demand renderer. It **also freezes the actual sailing clock** using heldAt/motionLag, while freshness continues on wall time (`sim/system.ts:79–86,130–164`; cross-check with S9DataSimCpu). The engine clock/systems/UI callbacks still run and `poseAt` still recomputes the held pose. Water/weather/light channels must be audited individually before declaring the canvas static. Pinning `?t=12` alone does not freeze boats or the world. Thus “static camera + reduced motion = no further renders required” is not established; cached held-pose calculation is a safer exact-work win than render-once.

### Governor and idle camera costs

- The governor changes quality/DPR based on cost, not viewer intent. Its timer-query path creates/deletes a WebGL query plus a wrapper object per measured frame (`governor.ts:103–128`), despite the class comment saying allocation-free. The 256-sample array is reused; insertion-sort percentile runs once per decision window, not every frame.
- Purposeful 30 FPS must not be interpreted as performance failure. `delta>21.5 ms` is currently a missed-frame signal and the GPU thresholds are calibrated around ~60 FPS (`governor.ts:136–165`). An idle cap must expose its target interval to the governor, or suppress cadence-derived downshifts while still measuring real render cost.
- A settled `CameraRig.update()` still recomputes trigonometry, `lookAt`, near/far, projection matrix and inverse projection every frame (`camera-rig.ts:78–93`). `CameraInput.update()` already early-outs when not gliding (`input.ts:121–126`). Dirty/snap-to-goal camera work is a safe small optimization; it does not justify a new architecture.

### React and picking

- No React state update is required for positions at frame cadence. `useFrame()` stores a callback in a ref and invokes it in the final `ui` WorldSystem (`hooks.ts:24–30`, `store.ts:106–127`). Hover and chart labels use `translate3d`, not per-frame React top/left state.
- The immutable UI snapshot changes at **1 Hz** for `tick`, on model identity changes, hover/selection and UI actions (`store.ts:95–101,115–125`). `HoverTag` subscribes broadly even while hidden; `Tag` and `PanelContent` broadly subscribe even when only model data is needed (`HoverTag.tsx:14–15,25`; `Panel.tsx:77–79`). Static panels can rerender for unrelated hover/tick changes. `BoatPanel` intentionally needs the whereabouts clock (`Panel.tsx:111–114`). `ChartLabels`, the shell and ledger use slices; the entire ledger is not rerendering at frame cadence (`App.tsx:14–17`, `Ledger.tsx:12–23`).
- Chart mode repeats layout reads: each `AnalyticPicking.screenPosition` / `waterline` calls `begin()` → canvas `getBoundingClientRect()` plus camera matrix update (`picking.ts:55–59,293–297,361–364`). Chart labels additionally read every label's `offsetWidth/offsetHeight` every frame (`ChartLabels.tsx:40–45`). The measured scene had 29 labels, with 26–27 rect reads and 29 width + 29 height reads per executed chart frame. Fleet already caches its own canvas rect until resize (`fleet-system.ts:1075–1085`); reuse that convention in the analytic picker, with appropriate invalidation for viewport/container changes.
- ChartLabels batches its first read loop before its write loop, which is good. However, boat leader `height` writes invalidate layout for subsequent frames; chart writes also precede the HoverTag callback in registration order. `HoverTag` writes visibility/dataset before reading `offsetWidth`, so a hover can force a synchronous layout (`HoverTag.tsx:29–44`). This is a **forced-layout risk**, not a claim that every rect read itself incurs a full layout. Cache label/tag sizes with ResizeObserver/font/content invalidation, collect frame projection context once, and only write changed strings.
- Chart scratch still allocates viewport object, `boxes.slice`, and `cullLabels` output each frame; landmark projection helpers create tuple/object data (`ChartLabels.tsx:38,56`; `picking.ts:241–254,370–374`). Prioritize redundant DOM reads ahead of tiny arrays. Fleet `screenPosition` also allocates a returned point object even when UIPicking has an `out` (`fleet-system.ts:1052–1068`, `picking.ts:416–422`).
- Pointermove merely marks the pointer dirty. Pick at most once per engine frame, or about every >120 ms with a stationary pointer; drags disable hover picking. Click/touch actions pick immediately (`store.ts:119–125,155–185,218–255`). No pointer means no repeated hover pick.
- **No GPU picking/readPixels and no full-scene triangle raycast.** UIPicking first uses fleet analytic ray/sphere and landmark segment tests; a boat miss falls back to screen-space hull/mast projections, heightfield marches, piers and zones (`picking.ts:407–414`; `fleet-system.ts:1022–1049`; `picking.ts:93–230`). The fleet landmark work is wasted when UIPicking discards a non-boat fleet hit; optionally expose boat-only picking, but profile before adding complexity. All instrumented phase windows recorded **0 WebGL2 readPixels calls**. The baseline capture warning must not be blamed on hover picking.

### Audio / season / ancillary

- Sound initially OFF: no AudioContext, synth import, synthesis, audio scheduler or controller polling. The controller object and one visibility listener exist, not a frame callback (`audio/controller.ts:150–153,178–193`). All sampled phases constructed **0 AudioContexts**. This is zero ongoing audio DSP/scheduler work, not literally zero bytes or listeners.
- Sound ON: `ambience.ts` is dynamically imported only after a user gesture or remembered-on first gesture (`controller.ts:144,177–193`). Playback uses native Web Audio buffer/oscillator/filter nodes. There is **no ScriptProcessor and no AudioWorklet**. Pure DSP in `dsp.ts` synthesizes PCM **on the main thread**, generator slices of 6144 samples; bank work runs nominal 2–6 ms idle budgets, or 4 ms fallback (`dsp.ts:1–6,43–44`; `bank.ts:76–97`; `ambience.ts:397–404`). These are source budgets, not measured elapsed guarantees: one generator step can overrun its requested budget.
- Audio enable also synchronously synthesizes 8.7 s white + 9.3 s pink stereo noise buffers (`ambience.ts:95–117,275–276`): at 48 kHz, **1,728,000 generated samples / 6.59 MiB final PCM**, plus temporary arrays. ClipBank comment budgets about 18 MB additional PCM; weather/season kinds are already lazy and sample rates already reduced (`bank.ts:9–27`). Do not re-propose those shipped wins.
- ON steady schedulers: ambience every 120 ms (8.33 Hz), world feed every 250 ms (4 Hz), and periodic replacement synthesis roughly every 20 s (`ambience.ts:92,393,684–690`; `controller.ts:191`). Hiding suspends AudioContext, **but does not cancel these JS timers or pending bank generation** (`controller.ts:145–148`). Audio time freezes, but unnecessary JS wakeups/input scans can remain.
- OFF after ON: polling stops immediately; ambience timer stops and audio fades/closes over ~680 ms (`controller.ts:265–270`; `ambience.ts:765–780`). This intentional audible fade is not zero work immediately after pressing OFF. A pending requestIdleCallback is not stored/cancelled; its inner callback can still call `bank.work` once after dispose, because `disposed` is only checked before scheduling (`ambience.ts:398–403`).
- Lifecycle gaps: Controller has no dispose/remove-visibility/disarm API; SoundToggle has no cleanup; neither UI store nor Engine dispose stops the sound service. Motion media-query listener also has no removal (`controller.ts:132–194,265–280`; `SoundToggle.tsx:10–14`; `ui/store.ts:346`; `engine.ts:277–289`; `ui/services.ts:64–78`). An engine unmount while audio ON can retain its context/engine and timers. This is an actionable source-level leak path, not a measured ten-minute leak slope. Ordinary full-page navigation unloads the context; the risk is same-document remount/HMR/viewport-gate transitions.
- Engine dispose also leaves `window.__harbour`, `__harbourProf`, dev `__harbourUI`, ready systems, services and AssetStore promise caches reachable until replacement; governor has no dispose for pending native queries (`engine.ts:102–103,277–289`; `ui/mount.tsx:11–14`; `assets.ts:15–18`). Renderer.dispose releases GPU state but does not delete JS geometry arrays retained by those graphs. Clear global refs only when they still refer to this instance; release source caches after asset consumers and asynchronous init settle. Establish one explicit owner instead of simply clearing maps before system cleanup.
- Season calendar already recomputes once/minute; keep that. Its daylight grade still recomputes a four-season weighted coefficient blend and allocates **3 arrays + callback per daytime frame** (`season-system.ts:167–182`). Precompute coefficients when weights resolve; multiply grade arrays in place after TimeOfDay resets them.
- TimeOfDay parses hex colors once and reuses Color/grade outputs, already shipped (`time-of-day.ts:217–229`). Unpinned local time allocates a Date and recalculates identical values within each second (`:205–214`). A cached local-hour base/second lookup removes up to 59 redundant Date constructions/s without quantizing any existing light output. Do not skip `apply()` blindly: Season and Weather modify its outputs after it each frame.
- Weather `step()` calls `targetsForLevel(shown)` and `split()` calls it again just to read gust: **2 target objects + 2 strikeKm arrays per active frame**, duplicate table/smoothstep work (`director.ts:61–74,182–217`). Pass the first resolved gust/targets to split or add an output parameter; preserve exact easing/data mapping.
- Analytics already deferred to requestIdleCallback (5 s timeout), absent when GA ID unset; no app-owned frame work (`google-analytics.ts:10–36`). Error reporter is event-driven, capped at 5 reports/session, hidden aborts pending work; do not remove diagnostic safety for nominal FPS (`error-reporter.ts:98–115,162–192`). One boundedness issue: `reportedKeys.add()` precedes the session cap check, so arbitrarily many unique subsequent errors can grow its Set (`:103–107`); low-priority correctness/memory hygiene, not an initial-load win.

### Power / vsync

These iGPU captures are hardware-backed AMD Raphael, not SwiftShader. The final separate 3 s timing window produced **4 / 10 / 14 FPS** (median 10), latest GPU timer values **57.53 / 54.55 / 58.75 ms** (median 57.53), after the quality governor moved to low. This is **not a steady 60 Hz idle energy measurement**: the iGPU was already bottlenecked/contended, and total process or device busy is not attributable to this tab on the shared host. Neither CPU% nor GPU-busy% nor watts at stable vsync was established. In particular, do not multiply these backpressured timer values by FPS to fabricate utilization.

A 60→30 ambient cap on a viewer currently sustaining 60 would submit **50% fewer complete world updates + composer frames [estimate, exact work-count ratio]**. At 120 Hz, capping ambient mode at 30 would submit 75% fewer. Watts do not necessarily fall by those percentages (fixed browser/display costs, GPU clocks, audio/network remain). A viewer already at ~14 FPS gains nothing from a 30 FPS cap. Reduced temporal smoothness of water, sails, boats and camera is **visual-risk**, not “none” merely because the camera rests. Offer an explicit low-power/ambient choice, preserve active inspection at the normal cadence, and judge 30 vs 60 in randomized **video** on both slow/faster weather and night beam. Still PNGs cannot approve it. With a capped loop, input/selection/resize/context restoration must invalidate immediately; return to active FPS on all input, including DOM/keyboard, not only canvas drag.

Include that under S9's quantified findings, not an extra additive LOOP saving. S10ShadersEnv identifies camera-dependent horizon caching (SHADER-15, `sky-system.ts:235–270` per peer) as a larger companion to a dirty camera; it reported S2 heap attribution of 27.1 MB sky.update self + 2.28 MB Math.hypot over 5 s, but those allocation causes are not proven by this slice. Reuse one camera-change signal rather than independent expensive matrix comparisons; leave live sky/weather time updates untouched.

## 5. Ruled out / not worth it

- **“Fix React updating all positions every frame”**: already imperative refs/transforms; no such React frame loop exists. Exact per-component profiler counts still deserve a clean follow-up, but broad framework rewrites are unsupported.
- **“Replace GPU readPixels hover picking”**: both pickers are analytic; zero observed readPixels during phase windows. Full-scene BVH/GPU picking would add complexity to an already throttled low-cost path. A duplicate fleet-landmark pass may be trimmed locally if a profile justifies it.
- **Render only on camera/data changes, including reduced motion**: not established safe. Full-motion boat trajectories remain live; under reduced motion actual sailing is held, but engine time, weather easing, freshness and time-of-day remain live inputs and not every shader is proven static. Render-once could freeze scenery or fresh/stale transitions. Prefer exact held-pose caching (S9) and camera-dependent horizon caching (S10) first. A true still mode requires an explicit product contract outside this slice.
- **Stop hidden-tab rendering**: already done by the engine. Remaining opportunity is audio JS and lifecycle, not another visibility renderer loop.
- **Use setAnimationLoop instead of rAF**: no automatic work savings; WebXR is out of scope. Keep boring current ownership unless a measured scheduling defect emerges.
- **Lower all DPR/quality to save memory**: renderer slice owns this trade; edge/sail/label appearance is not free. VRAM estimates show quadratic cost but do not establish marginal visual impact.
- **Virtualize the ledger by default / memo everything**: no evidence ledger DOM dominates ordinary frame CPU; ledger uses slice subscription and is absent when closed. Preserve accessible complete table semantics.
- **AudioWorklet for all existing synthesis/playback**: playback is already native graph DSP, not main-thread ScriptProcessor. A dedicated worker for clip preparation is a more direct conditional fix than rewriting the graph in a real-time worklet.
- **Further eager preloads for ambience**: audio is OFF by default and lazy; pulling 40 KB synth into world boot spends bandwidth/parse cost for a disabled feature.
- **Re-synthesize lower-rate/lazy audio kinds**: already implemented (`bank.ts:9–27`).
- **Remove analytics/error reporting for FPS**: app-owned logic is not per-frame; analytics already deferred. Third-party GA task/network cost was not isolated in these dev samples, so no invented milliseconds saved.
- **Treat stable81 geometries over seconds as leak-free**: unsupported. Likewise heap drops after GC are not a leak fix.

## 6. Open questions / measurement prerequisites

1. **Required missing evidence:** reserve one measurement-owner long-session slot (≥10min) after the queue clears, with live data, no interaction, stable quality/DPR, periodic heap/renderer counts, and a 12-refresh/remount sequence. Current short-hook measurements cannot satisfy the ten-minute/refresh-soak acceptance numerically. This is the only substantive evidence blocker; code research/report is complete.
2. Actual steady CPU% / GPU-busy / watts on an idle vsync-sustaining iGPU viewer needs an isolated device/process interval, not whole-device counters on this18-agent shared host. S2's baseline matrix should establish render costs; a quiet hardware session is still needed for energy claims.
3. Is an explicit user-selectable 30 FPS ambient/low-power mode acceptable? If the no/marginal appearance requirement is absolute, do not auto-enable it until video review shows acceptable motion. No operator decision is needed to implement the exact-work eliminations above.
4. Exact per-component render invocation counts need a clean React Profiler/counter spike (production profiling build or explicit function counters) rather than interpreting stale committed-fiber flags. Root commit counts already show the absence of a frame-rate React update problem.
5. Does the viewport-gate/remount path occur often in production (foldable resize, desktop window gate, navigation), or mainly dev HMR? Lifecycle ownership should be corrected either way; this determines expected real-user memory gain, not source-level leak validity.
6. Audio-ON initial-enable and steady CPU profile is still needed before spending on a worker. No auditory/motion degradation has been accepted by this report.
