# SP-SIMRACE — deterministic initial simulation preparation

## Verdict

**Promote BOOT-01 / DATASIM-01 / LOAD-01 as one implementation item, not three additive savings.** The first-frame fallback is a reproducible ownership race, including a second window after eager planning but before path completion. A single-owner prepared candidate removes initial generation from animation frames without changing the simulation algorithms.

In three contended dev runs per final condition, first `u:data` fell **1640 / 1726 / 1763 ms → 0 / 0 / 0 ms** (engine-rounded). First completed frame median fell **3294.5 → 1437.3 ms**, but the new first frame is deliberately an honest empty/awaiting frame. The meaningful fleet metric improved **3294.5 → 2784.6 ms median**, a **509.9 ms / 15.5%** observed improvement, not a 1.86 s fleet improvement. Quiet production-bundle repeats are still required before assigning a release threshold.

DATASIM-02 remains worthwhile: the exact compact seed is **48,934 B Brotli**, parses in **1.321 ms median**, and preserved plans, initial poses and **2487 path comparisons** across three scenarios × three repetitions. It was evaluated independently, not included in the browser speedup above.

## 2. Exact root cause and timeline

### Two independently unsafe windows in HEAD

Source anchors below refer to unmodified HEAD:

1. `data/fetch.ts:129–135` starts **all seven endpoints concurrently**. Every success **or failure** installs a snapshot and notifies subscribers (`144–167`). `sim/system.ts:89` turns any notification into `dirty = true`.
2. The early task is gated on **all seven initial endpoints AND `warm.done`**, then a zero-delay timer (`system.ts:105–107`). `warm.done` means the required messages have been *delivered on the main thread*, not just that worker CPU has finished.
3. Engine initialization continues; its first frame is scheduled independently (`engine.ts:123–145,168–177`). When `DataSystem.update()` sees dirty data, it immediately calls `rebuild → setModel → install → buildPlan`, followed by `poseAt()` (`system.ts:148–164`; `sim.ts:353–410`). There is **no first-install preparation guard**.
4. Therefore, if **any endpoint notification precedes the first update and the early task has not consumed the dirty state**, the frame owns the real install. It can build from a partial payload set; all seven need not be complete. Any leg/outing answers not yet adopted are computed synchronously by the plan, and current uncached routes are built by the first pose.
5. Even if the early task wins, it publishes the real model and mutates the registered sim **before awaiting `warm.paths()`** (`system.ts:123–127,140–145`). A frame during that await can call `poseAt()` and build unseeded paths itself. A further endpoint notification can also trigger another install while that path job is pending; plan-identity checks then discard results for the old plan. The `eager` flag only prevents another early task, not frame consumption.
6. When the frame wins first, the eventual early task finds `dirty === false` and terminates the workers (`system.ts:117–120`); their initial-path phase never runs. More workers cannot repair this ownership problem.

A cheap first `u:data` can thus mean: no payload has arrived yet; a real eager install and its paths finished in time; or only cheap remaining pose work was due. It is not alone proof of correct initial readiness. A long `u:data` can contain cold plan work, cold paths, or both. This explains why p1's 3–6900 ms range and an eager long task followed by another expensive first update are compatible observations. This spike proves the mechanism, not an exact stack attribution for p1's particular c-cold-1 task.

## 3. Minimal prototype and before/after distributions

### Implemented behavior

`sim/system.ts` now has one queued preparation owner, seed readiness, a feed revision, an unpublished candidate and a small `simPreparation` service:

- Subscriber callbacks mark dirty, increment revision and request a task; animation frames never call `rebuild`.
- Initial preparation waits for the coast/sim, warm completion and **settled stablecoins + pegSummary snapshots**, not the other five endpoints. Stablecoins determines eligibility, circuits and class; pegSummary determines active depeg/Shoals state (`model/build.ts:65–110`). A failure snapshot also counts as settled, preserving unavailable/stale truth; it is not replaced by a fixture.
- Construct a separate empty candidate, seed exact leg/outing answers, install the real model in the task, ask existing workers for its `now`/`soon` paths, and await every `now` response.
- Keep the registered empty **model and sim together** until candidate poses exist. New readings with the same plan key coalesce into the candidate before publication. A genuinely changed key discards the invisible candidate and stops the obsolete path phase; an unseen intermediate version never causes a launch/rejoin event.
- Run the initial full pose **in the task**, covering worker failure and UTC segment-boundary misses. Publish model, sim and revision atomically in that same task. The first consuming update uses that already-prepared pose once, rather than immediately duplicating its evaluation. This can make the first displayed pose about one frame old; it does not alter the route or clock rules thereafter.
- Initial awaiting frames do not pose an unfinished real sim. Later dirty refresh installs also move to a task, retaining the previous coherent version until then. This is not a persistent off-thread refresh implementation.
- `warm-legs.ts` now settles pending warm/path promises on stop, including partial worker-construction failure. Without this, replacing the opportunistic fallback with a mandatory preparation barrier could leave a partially constructed warm pool pending forever.
- `app/harbour-app.tsx` additionally requires preparation readiness before the existing four-frame reveal watch starts. The existing eight-second honest no-data timeout is retained. A raw fetched stablecoin snapshot no longer makes an unfinished fleet count as prepared.

No plan, hull, route, collision, separation, eligibility, data mapping or render-quality algorithm was relaxed. The extra isolated candidate costs one additional layout build: **69.7–79.9 ms**, median **77.1 ms**. Keeping that bounded, one-time isolation cost is preferable to sharing mutable candidate raft slots with a public runtime in the first implementation.

### Diagnostic mistake caught and fixed

The `after-*` group is **not** the delivered pipeline. It produced first-boats **3920.7 / 4078.1 / 4280.6 ms** despite cheap first data updates. It exposed two invalidations: initial truth rechecks compared against the empty model while a candidate was pending, and nonstructural late endpoint arrivals discarded an already-warmed candidate. That rebuilt two real plans and rebuilt ~285–292 main-thread routes after stopping workers. The final version suppresses truth rechecks until the initial coherent version exists, and coalesces same-plan readings before adoption. These diagnostic captures are retained because “cheap first frame” alone would otherwise have hidden a fleet regression.

The before/final samples are consecutive groups, not a randomized paired trial; API completion and machine contention differ. The source invariant and removal of frame generation are high-confidence. **509.9 ms is an observed dev improvement, not a guaranteed live-site saving or a quiet-device budget.**

## 4. DATASIM-02 — compact build-time seeds

Reused the p1 compact seed, excluding the generation-only lane-distance grid. Parsed the real WebP coast channel with the same row reversal as runtime. Compared ordinary cold planning against an empty candidate seeded with JSON-round-tripped answers, then compared every requested initial `now + soon` route (`PathRec` arrays and bad-outing flag), full plan boats/statistics, and full initial pose buffers using Node strict deep equality.

| Scenario | Boats | Unique initial requests | Repetitions | Exact path comparisons | Plan + pose equality |
|---|---:|---:|---:|---:|---|
| Saved live fleet | 623 | 313 | 3 | 939 | 3/3 |
| Synthetic fleet, real harbour, current fixture epoch | 625 | 199 | 3 | 597 | 3/3 |
| Live supplies +0.1%, genuine class-boundary crossing | 623 | 317 | 3 | 951 | 3/3 |
| **Total** | — | — | **9** | **2487** | **9/9** |

Seed size: **462,618 B raw / 72,099 B gzip / 48,934 B Brotli**, corroborating p1. Seven batches of fifty JSON parses: **1.298 / 1.321 / 1.353 ms min/median/max per parse**. Seed-adopt + real-plan medians, excluding layout and path generation: **417.8 ms live**, **1087.4 ms synthetic**, **384.3 ms perturbed live**. These are different scenarios, not a paired browser seed speedup; the high synthetic allocator cost confirms that immutable answers are not the entire planning problem.

Recommendation: generate the full compact seed alongside authored harbour assets, using the current `legTimes` + `outingSeed`, with exact JSON float round trips and `lanes:null`. A 48,934 B Brotli asset occupies approximately **43.5 ms at 9 Mbps**, plus discovery/RTT, versus repeated immutable computation in multiple realms. Main parsing here is ~1.3 ms. Expose it through a content-addressed build import/preload and pass the same seed to each path worker; workers still construct their own layouts and compute live-plan paths. Do not run the existing outing generator again after valid adoption.

Version inputs must cover authored layout, decoded coast bytes/SDF version, hull dimensions, and the transitive geometry/timing/outing algorithms/constants. Generate the reference and seed together; compare their digest in generation/CI, rather than hashing a 4 MB coast on every navigation. A changed authored layout in development may compute answers in the preparation task, never in `update()`. Do not silently adopt a mismatched seed.

The **1,036 B Brotli representative-times-only** option remains a byte-minimal alternative (p1 measured). In this four-worker setup, however, worker0's ~193–227 ms outing stage still gates warm readiness when leg shares become cheap. Full seeds remove that and repeated ~167–181 ms outing work in the other workers too. Current warm-critical compute after each layout is roughly **0.2–0.26 s**; therefore an additional **0–250 ms fleet wall-time gain is an estimate**, depending on overlap, not the ~1.5 s aggregate multi-worker CPU one might incorrectly add up. The ~0.5 s allocator and actual path generation remain.

## 5. Implementation-ready production design

Land one bounded initial-preparation change first, following the prototype's existing `HarbourSim`/worker APIs rather than introducing a second simulation:

1. **`sim/system.ts`: explicit state ownership.** Retain `awaiting → preparing(revision) → ready(revision)` and one queued owner. Capture endpoint snapshots at task entry. Keep both public model and sim empty until the first complete candidate. Essential eligibility/state endpoint errors settle honestly; other endpoint truth remains unavailable until received. Never let `update()` call model installation or initial path generation.
2. **Candidate coherence.** Use a private candidate with exact existing seeded methods. Before adoption, coalesce same-plan readings; discard structurally superseded initial versions. Do not generate transition voyages against an unpublished version. Resolve freshness against the real clock, preserve dev/reduced-motion sim clock semantics, and cover segment-boundary path misses in the task. Publish a single revision only after a valid pose exists.
3. **`warm-legs.ts` / worker lifecycle.** Keep current transferred path buffers and plan-identity checks. Pending operations settle on construction failure, worker error and disposal; canceled or superseded jobs cannot publish. Once a worker's `soon` phase is underway, do not reuse its handler for a newer plan: stop that pool on structural supersession or introduce an explicit job id if making it persistent. The prototype uses the former, simpler policy. Worker failure fallback is still exact computation, but only inside preparation tasks.
4. **`harbour-app.tsx` and FleetSystem readiness.** Keep the current timeout and honest awaiting fallback. Initial readiness must refer to the prepared revision, not raw feed presence. The prototype keeps the existing four-frame watch after preparation; a later BOOT-05 refinement can replace it with explicit `fleetRenderedRevision === preparedRevision` after composer completion. Do not claim a fetched snapshot or an empty scene-only first frame is a ready live fleet.
5. **Optional seed asset in the same cutover.** Adopt the full versioned compact seed before any real plan, in main candidate and path workers. Remove production duplicate immutable generation after valid seed adoption. No all-pairs path asset, no slot quantization, no route simplification.
6. **Do not overclaim off-thread planning.** This first change still has a ~491 ms main-thread plan task in the measured live scenario. A persistent planning worker/sliced exact allocator is a distinct DATASIM-03 change. A worker version needs an explicit cloneable plan representation for arrays/maps plus reconstruction of `legSeconds`/`laneMetres` closures; blindly structured-cloning `Plan` will not work. That larger change is not necessary to establish deterministic initial ownership.

## 9. Ruled out, remaining risks and decisions

- More workers, earlier worker-script preload, or waiting for all seven APIs are not ownership fixes. Workers already start alongside API/SDF; all seven had completed before every baseline fallback.
- Moving the unchanged monolithic plan into a timer improves frame ownership, not total main-thread responsiveness. Do not advertise removal of all long tasks.
- Do not count the newly early empty first frame as faster boats, nor suppress a true class-boundary replan. Do not use less precise routes, omit boats, or ship all-pairs route samples.
- The prototype intentionally retains the existing synchronous later-path/lookahead machinery and main-thread refresh install algorithm, now scheduled outside the frame. Stale initial installs can themselves pose while freezing inside `HarbourSim.install`; that remains off-frame here, but is a reason to separate plan construction from freeze/pose in a future fully off-thread job.
- Dev cold module loading and local API timing are not production-bundle/CDN behavior. P1 already corroborates the race on production-faithful4180; this spike did not remeasure a bundled variant.
- No operator decision blocks the initial prepared-job fix. Choose the additional49 KB full seed versus1 KB leg-only seed on the quantified byte/CPU tradeoff; recommendation is full compact seeds after digest/equivalence coverage. No change to the world meaning or timeout policy is requested.

The isolated dev server was stopped after captures. The patch preserves everything needed to recreate the prototype; the throwaway worktree and branch are removed at handoff. No push or commit was made.
