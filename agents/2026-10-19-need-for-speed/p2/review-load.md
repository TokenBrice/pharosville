## Critical-path model and realistic end state

### Ground truth and units

`p1/load.md:21–50,77–90` and raw `load/summary.json:75–145` establish:

- Cold fast4g first fleet-bearing frame **5,943.6 ms**, crossfade **6,088.9 ms**, poster removed **7,203.9 ms** (n=3 medians); unthrottled **2,974 ms**; fast4g + 4× main-thread throttle **9,973 ms**.
- Representative successful fast4g: engine constructed 1,578.5 ms; stablecoins parsed 2,221.6 ms; SDF ends 2,711 ms; island ends **4,265 ms**; civic/kit bytes end **5,289/5,425 ms**; first update/render **429 ms**, including data 4, ocean 211, fleet 60, composer 125 ms. Eager CPU long task 3,184.5–3,712.5 ms lies *inside* the island network wait.
- Fast4g means **9 Mbps / 40 ms**, approximately **1,100 bytes/ms** practical planning throughput. The register's repeated 1.6 Mbps equivalents are legitimate alternate-network arithmetic but must not be used as this program's baseline. E.g. island Brotli saves ~155 ms occupancy, not 850 ms here; a 43 KB stage file ~39 ms, not 216 ms.
- Crossfade duration is an additional **~1.1 s**, not a part of first-frame network/CPU. The 145 ms observed reveal gap includes scheduler/deferred work as well as ~50 ms fixed settle floor.

Use this dependency model, not the sum of awaited system laps:

```
T_first_fleet = max(T_geometry_ready, T_prepared_model_pose, T_other_required_state)
                + C_final_commit_update_render
T_geometry_ready ≈ L_dependency + B_contending_critical / R + C_unhidden_prepare
T_crossfade_start = T_first_qualifying_render + D_readiness_delivery
T_poster_removed ≈ T_crossfade_start + 1.1 s (default motion)
```

CPU under an outstanding transfer is not automatically serialized CPU. Worker aggregate CPU is not wall time. Warm-up moved from the first draw to a serial pre-draw block has zero total-load saving unless work is actually removed or overlapped.

A useful **calibrated [INFERENCE]**, not a new byte measurement, is `5.425 s ≈ 0.152 s + 5.8 MB / 1.1 MB/s` for the geometry frontier, followed by **0.519 s** to the observed frame (includes final CPU/submission/observation). The raw median completed-before-frame count is 5.781 MB, but that is not an exact critical-byte tally: it excludes partial responses and includes nondependencies. Calibration prevents pretending all ~7.8 MB full-session traffic blocks the first frame.

### T1 + T2 forecast (healthy API, standard GPU, 9 Mbps)

**Planning forecast, not a gate or measured combined result: first fleet ~4.7–5.2 s; crossfade starts ~4.75–5.3 s; fully revealed ~5.85–6.45 s with the unchanged 1.1 s fade.** A practical central target is **~5.0 s fleet / ~6.2 s fully revealed**. Do not promise sub-4 s from the current evidence.

Derivation: start at the calibrated 5.425 s geometry frontier. Subtract exact asset 644 KB, roughly 60–85 KB of successfully separated initial UI/narrative code, and **0–164 KB** equal-codec API projection benefit actually contending before that frontier; add **49 KB** if adopting full compact sim seeds. This gives a net network occupancy improvement of approximately **0.60–0.77 s**, not seconds per row. At the optimistic end, coherent scheduling may recover up to ~0.15 s of *unhidden* dependency/commit gaps; this is a sensitivity assumption, not the register's unproven 1.2 s scheduler promise. Budget **0.25–0.45 s** residual final commit/update/render instead of deleting the original 0.519 s wholesale. Rounding and an allowance for contention/browser overhead yield the forecast above. If exact-sea reconstruction fails its CPU/memory gate, add roughly **0.2 s**; if API projection is not approved, use the upper part of the range.

Model readiness must still fit under geometry readiness. NFS-001/006/007 make that reliable; they do not earn another 0.5–2.3 s subtraction on this fast4g median. `sp-simrace.md:113–150` proves only **510 ms fleet** improvement in contended unthrottled dev runs; the 1.857 s first-engine-frame improvement is an earlier **empty awaiting frame**. Full seeds remove an estimated **0–250 ms warm-critical compute** while adding ~44 ms wire, not 0.65 s times four workers. The ~0.49 s main allocator persists until NFS-007. The byte frontier can become CPU-limited as it moves earlier; rerun the max() branches rather than extrapolating linearly.

With separately approved RGB6/high, the additional byte ceiling is ~0.276 s. A **~4.4–4.9 s fleet / ~5.6–6.1 s fully revealed** stretch range is plausible [INFERENCE], consistent in scale with the 4.728 s local full prototype, but not an approved T1/T2 commitment. A 600 ms fade could then remove another ~0.5 s from *poster removal only*; exclude it from the default forecast.

The 4× CPU baseline (~10 s) and one iGPU cold sample (~8.8 s) are separate bottleneck regimes. No spike supplies a production-bundle, quiet, combined 4× CPU end state. Do not publish a numerical device guarantee from a byte model: retain full CPU-throttled and iGPU fleet/reveal/tail acceptance lanes.

### Repeat-visit end state

Current immediate repeat first-fleet medians are **2.74–2.96 s**, despite only **106–176 KB site traffic**. Ten/eleven real 304s total 208/536 ms request-duration sum; they overlap. Fingerprints eliminate validation **waves**, not nine sequential RTTs, and do not save the already-cached island body a second time. Long repeats (>60 s), same-deploy immediate repeats, cross-deploy repeats and back/forward restores must be distinct arms.

After coherent fingerprinting/manifests plus deterministic preparation/seeds, a conservative **~2.2–3.0 s first fleet, ~3.35–4.25 s poster removal** is a planning envelope [INFERENCE], not demonstrated end-to-end performance. Persistent last-good payloads contribute **zero guaranteed healthy-repeat reveal gain** because the network already arrives before the scene. They help slow/offline repeat visits only; they do not persist GL resources, compiled JS execution, scene construction or simulation plans.

NFS-039 requires a product decision: preserve original `fetchedAtMs`, original `_meta`/age/updatedAt/status and endpoint identity; add elapsed time on hydration, never relabel a stored response fresh. `model/truth.ts:12–19` currently computes `meta.ageSeconds + sinceFetch`; `data/fetch.ts:159–162` preserves the old timestamps on errors. Hydrate only after admission, validate schema/version, cap age, reject unusable snapshots, and race storage versus fresh network by revision so a late disk read cannot overwrite new data or provoke duplicate expensive initial plans. Missing/quota-denied storage must leave normal network startup unaffected. Clock rollback/unknown freshness cannot become evidence of freshness. Honest stale hydration may intentionally show fog/frozen boats/dim landmarks: mapping-neutral is **not pixel-neutral** against a fresh visit. Prefer native HTTP caching for immutable media; do not add a service worker as a prerequisite.
