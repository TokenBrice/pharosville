## Scope and evidence standard

Research only. Covers every NFS-057–104 (A.5–A.8), runtime implications of B/D, and F.2 approval boundaries. Evidence labels: measured = an existing cited experiment, with its limitations retained; **[estimate]** = unmeasured saving; **[proposal]** = acceptance target, not an achieved result. Logical bytes, fragments, resident program counts and GPU milliseconds are different measures. None of the following per-entry savings may simply be summed.

## Executive judgment and audience

1. **RTX desktop at DPR1 is not the steady GPU optimization customer.** The brief's ordinary capture is vsync-bound; p1/frame's uncapped RTX samples show ~1.15–1.93 ms latest GPU time with host/CPU pacing. CPU savings buy headroom and possibly power, not demonstrated higher visible FPS. Multi-second runtime shader/plan hitches still matter on otherwise fast hardware.
2. **Raphael is genuinely a GPU-stress case, not a representative laptop CPU.** The captured GPU identity is the integrated Radeon on Ryzen 7 7800X3D (Raphael, the task's 2-CU proxy), paired with a fast desktop CPU. It establishes a weak integrated-GPU floor, not a universal Intel/AMD/Apple laptop baseline. p1's 52–80 ms are latest query samples, not medians; uncapped rAF p50 2–4 ms is not completed-frame throughput. Shader/GL waits dominate some windows. Representative laptop hardware and thermal/battery runs remain necessary.
3. **DPR2 laptops are likely pixel/memory limited [INFERENCE], not measured by p1.** Four times DPR1 screen pixels does not mean four times total cost: wake/history/shadow work is fixed-size. A strong laptop iGPU can outperform this proxy substantially. Neither claim licenses silently reducing image quality.
4. **Fix hitch ownership before polishing fractional milliseconds.** sp-hitch reproduces Medium→Low: 23 new programs and 4,405.7 ms median longest synchronous driven frame (n=3, contended). Diagnostics-off plus correct target still stalls 6,085.1 ms: reflection waits replace info-log waits. Bloom tier changes dispose reusable materials. Correct target is useful but not the whole fix.
5. **Preserve motion as scenery.** Static reduced-motion PNGs cannot approve lower-rate boats, shadow cadence, reflection cadence, AA shimmer, or an ambient 30 FPS policy. Existing Low tiers already change visible lighting/shadows/halo breadth; “same art” in quality.ts is not visual equivalence evidence.

## Governor: what exists and what should change

Actual source: `src/harbour/engine/governor.ts:44–57,90–178`, `quality.ts:27–58,71–84`, `engine.ts:87–90,266–274`.

- Already one GPU-aware controller: 90 frames OR 1.5 s windows, p10 from up to256 query samples, slow-share threshold6% over21.5 ms or GPU>13 ms, CPU-bound hold unless GPU≥60% of average interval, hysteresis/cooldowns, conservative recovery (<6 ms projected next rung), timerless backoff probes. Do not propose this as new work.
- DPR1 collapses to High/Medium/Low **all at1**. Falling to Low does not reduce screen fill. DPR2 has seven coupled tier/DPR rungs; the existing ladder already tries pixel reductions within a tier. There is no automatic sub-DPR1 fallback.
- `go()` publishes synchronously. Cooldown prevents a bad control decision after a compile, but does not hide the hitch from the visitor. Lights change16/8/4 slots; SMAA changes defines; bloom level resizing destroys shader materials. DPR-only changes create no new program keys in sp-hitch, but its measured resize setup costs37.2/113.1 ms (baseline/composite variant medians), so continuous resolution resizing is not free.
- **Order:** fix exact initial light state + compiler target + bloom material ownership; introduce complete next-state preparation before tier publication; keep current tier drawing while preparation is pending. Only then evaluate separating scale choices from effect tiers within the same governor. Prefer bounded, infrequent measured decisions over an arbitrary mandatory0.05 step. Smaller steps can mean more reallocations and a much slower descent on a weak GPU.
- Do not warm future tiers by publishing them and switching back: live material `currentProgram` can change underneath compileAsync polling. sp-hitch §5 gives the preparation-owned material/state contract; one adjacent state, bounded lifetime, cancellation and no visible intermediate tier.
- NFS-071 must not reduce query samples without redesigning the decision sample threshold: >20 samples currently required; 1-in8 of a90-frame window yields about11, causing fallback to the timerless inference. Preserve query validity/decision semantics before claiming microseconds.

## Memory accounting and iGPU priority

`p1/pipeline.md:57–78` source-derived target inventory is more useful than a guessed FPS gain: at1600×1000@1 screen-dependent targets~90.54 MiB; at2560×1440@2~834.37 MiB. High fixed targets push the latter to~1059.37 MiB before meshes, asset textures, canvases, swapchain and driver overhead. Low shadow saves96 MiB relative to High, but barely changes screen-dependent bloom storage. These are logical allocations, not measured resident VRAM. On shared-memory iGPUs they compete with CPU arrays/decoded images and can increase bandwidth/pressure, not merely consume a dedicated VRAM pool.

Prioritize exact ground ownership/bake004, placeholder right-sizing017, scalar lettering099, lifecycle101, and conditional depth-copy077 before lossy atlases or visual sea downsampling. Distinguish persistent bytes from boot peak (old+new canvas, parsed+merged geometry, worker copies), and sample context losses/remount plateaus. Program prewarming also consumes retained program memory: fix wrong variants and eviction before retaining more. Do not add004+101 ground disposal twice, or016+017+031+098 atlas savings against the same original atlas.
