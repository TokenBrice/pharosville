## Missed risks

1. **The "30d" disclosure surface is a hardcoded string, not just a policy question.** `gardenMonthRecordLedgerClause` emits the literal "Garden record, 30d" (and the ledger's "Worst band, 30d") regardless of actual span/samples, while only the label body discloses `spanDays days on record` (`accessibility-ledger.test.tsx:510-511` pins both). If the operator adopts open-decision 4's "disclose sample/span limitations", the fixed "30d" clause text — owned by the DOM/truth owners the report names (U0/S1) — is the concrete string to revisit; the report states the disclosure idea but never names this string.
2. **Program-cache hazard scoping (see Design audit):** the report sells key collision as a live hazard for the current pair; in fact standard parameters already separate the two programs. Worth restating accurately so a future reviewer doesn't infer that `customProgramCacheKey` equality today means the two owners currently share a compiled program (they do not — the probe compares patch keys, not compiled programs).
3. **Existing pinned drawable count as a free guard:** `garden-island.test.ts:~204` already asserts `expect(after).toBe(42)` drawables after merge; the report's Δowners=0 budget could cite this existing oracle instead of only the scratch inventory (small robustness gain, no change required).
4. **A2 probe caveat:** the report's throwaway "default vs explicit Danger compile identically" check must build both arms from the same *function-level* material parameters; the real owners differ in `flatShading`/`roughnessMap`, so an owner-level comparison would differ for reasons unrelated to the profile. The design's wording (function-level probe) is fine; executors should not upgrade it to real-material comparison.
